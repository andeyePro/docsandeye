# Spec Critique — cycle 1

## Concerns

1. **[AC6, AC7] BLOCKING — semver comparison semantics unspecified.** "Semver comparison, not string equality" (AC7) and "future pin" (AC6) never say whether comparison follows full semver precedence (numeric field ordering, e.g. `1.10.0 > 1.9.0`), whether pre-release identifiers (`2.0.0-rc.1`) are legal in `design_version`/pins/changelog `version` at all, and if so how they order against release versions, or whether build metadata (`+meta`) is stripped before comparison. A Generator using naive string comparison or a strict-release-only `semver` config would satisfy some tests and fail others depending on which the Tester happens to pick; there is no normative answer to check against.
2. **[AC1, AC7] BLOCKING — changelog entry `version` is never schema-validated.** AC1's component-rejection list validates `design_version`, `kind`, `master_format`, `supersedes`, `source_files`, but not each `changelog[].version`. AC7's changelog-range rule `shot_with < version <= current` requires every changelog entry's version to be a comparable semver; a malformed or non-semver changelog version makes the range computation undefined, and no AC says whether `parseComponent` must reject it.
3. **[AC7] BLOCKING — "byte-identical across two runs" does not test "sorted keys".** The data-model section asserts `staleness.json` has "keys sorted, deterministic", but AC7's only test is that two runs of `JSON.stringify` are byte-identical — a pure function with unsorted-but-consistent (e.g. insertion-order) keys trivially satisfies that. A Generator can pass the letter of AC7 without ever sorting keys. Needs an explicit assertion like "top-level keys equal media ids in lexicographic order" independent of run-to-run identity.
4. **[AC9] BLOCKING — the render job's `parameters` field has no defined source.** The Step `renders` entry (data model) carries no `parameters` key at all, yet the render-plan job schema has a `parameters` object that feeds the hash. Is it always `{}`, is it copied from the referenced component's top-level `parameters`, or something else? The one worked example shows `"parameters": {}` for a component not shown elsewhere, so it proves nothing. Since `parameters` is half the input to the params-hash, an ambiguous source makes the hash itself unverifiable by an independent Tester.
5. **[AC9] BLOCKING — dedup/key rule for `hand-exported` (f3z/none) jobs is undefined.** Normal jobs dedup "by key" where key encodes `render_id` and a params-hash of `{parameters, options}`. Hand-exported jobs have no render options and the spec never gives their `key` format, nor says whether two different step renders/viewers of the same f3z-mastered component collapse to one hand-exported job (there is nothing to distinguish them) or produce one duplicate-output job per reference. A Generator could go either way and cite "dedup by key" for either behaviour.
6. **[AC5] BLOCKING — denylist glob dialect and multi-segment `**` semantics unspecified**, despite this being the exact loophole risk flagged for review: is `private-notes/**` matched with `minimatch`/`micromatch`/`picomatch` defaults, does it match `private-notes` itself (zero extra segments), and does it match nested paths like `private-notes/x/y.md`? The one fixture (`private-notes/pi02-setup-notes.md`, single extra segment) passes under every plausible dialect, so AC5 as written cannot distinguish a correct implementation from a naive `path.startsWith(prefix)` check that would misbehave on `.claude/**`/`.vibe/**` in real projects.
7. **[AC2, AC14] BLOCKING — guide-default application has no owner function.** The data model says a step's `guide` "defaults to `config.guides[0].id`", and AC14 assumes `guide` arrives "defaulted" by the time `stepsForGuide` runs, but `parseStep(text, filename)` takes no config and AC2's explicit defaults list (cat/explode/annotate/format) omits `guide`. Nothing states which function actually resolves this default (`loadProject`? `stepsForGuide` itself, given a config?) — a Generator could leave `guide` unset entirely and pass AC2 while breaking AC14 on any step that omits `guide`, or vice versa.
8. **[AC4, AC11] BLOCKING — real contradiction between a closed provider enum and a runtime-extensible registry.** AC4 requires `parseConfig` (no registry argument) to statically "reject an unknown hosting provider," implying a fixed enum of known names. AC11 requires `registerHostingProvider(name, impl)` so a provider can be "used by name in config" — i.e. validated dynamically against whatever is currently registered. As written, a config naming a provider registered after schema compile time must simultaneously fail (AC4) and succeed (AC11); the spec never reconciles config validation with the registry.
9. **[AC12] BLOCKING — not mechanically verifiable by a vitest test, and "offline-tolerant" is undefined.** `npm install`, `npm run build -w …`, and `npm test` are shell/process-level assertions; the Test location section says tests live under `packages/core/test/` as vitest specs, which cannot themselves invoke `npm install` in any meaningful sandboxed sense, let alone assert absence of network calls. "Offline-tolerant" has no operational definition (a populated npm cache? `--offline` flag? no lockfile drift?). This AC needs either a named shell-level check outside vitest or should be dropped from the Tester's mechanical scope.
10. **[AC2] BLOCKING — render entries' required fields (`component`, `view`) are not in the rejection list.** AC2 only names `order`, duplicate render `id`, and unknown `cat` as rejection triggers. If `component` or `view` on a `renders[]` entry is missing, nothing says `parseStep` must reject it — an omitted `view` would flow silently into the render-plan `options` object (AC9) as `undefined`, corrupting the params-hash JSON.stringify output in an implementation-dependent way.
11. **[AC1, AC6] MINOR — `problems[]`/`DocsiError` field shape is inconsistent across ACs.** AC6 pins down `{code, file, path, message}` for cross-reference problems; AC1 only requires "the YAML path … and file name" for parse-rejection problems, leaving `code` and exact key names undecided there. Tester and Generator could reasonably disagree on whether AC1's `DocsiError.problems[]` entries need a `code`.
12. **[AC4] MINOR — the default denylist's exact contents are only shown as a YAML-comment example, never stated normatively.** "Defaults merged in even if omitted" implies the three-entry array in the data model IS the default, but AC4 doesn't reproduce or fix that list as a testable value, so a Tester asserting the merged result must guess it from prose rather than spec text.
13. **[AC11] MINOR — "single slash joined" doesn't specify the join algorithm for a `base` without a trailing slash.** The only example has `base: "https://media.example/"` (trailing slash). If `base` lacks one, does `resolveMediaUrl` normalize (strip/insert) or does naive `base + file` concatenation (which would then be broken) satisfy the AC? Recommend requiring the join to be robust to either form and adding that case to the fixture.
14. **[general] MINOR — the `aep-like` fixture's guide-count requirement for AC14 is implied, not stated.** AC14 needs the fixture's config to declare ≥2 guides so "a step shared by two guides" is possible, but the Repository-layout fixture description never lists this requirement alongside its other cardinality constraints (≥4 components, ≥3 steps, etc.).
15. **[AC10] MINOR — the shape of a "violation" returned by `checkVersionBumps` is unspecified** (component id only? both commit shas? a message?), leaving Tester and Generator free to invent incompatible shapes that both satisfy "returns a violation for every component… and none otherwise."

## Iteration 2 — Concerns

1. **[iter-1 #1–#14] RESOLVED.** Release-semver rule (Versions section), changelog `version` validation (AC1), `staleness.json` key-sort assertion (AC7 walks the parsed tree), render-job `parameters` source (job rules), hand-exported dedup/output rule (job rules, explicit two-jobs-same-outputs example), denylist glob dialect + exact test table (AC5), guide-default ownership split between `parseStep`/`loadProject` (Step data model + AC2/AC5/AC14), the closed-enum-vs-registry contradiction (AC4's `{registry?}` param and default/fresh-registry test), AC12's shell-vs-vitest split, missing-field rejection for `renders[]` (AC2 now includes "without `component` or `id`"), the single normative `Problem` shape, `DEFAULT_DENYLIST`'s literal contents, the `url-prefix` join algorithm, and the 2-guide fixture requirement are all now precisely specified and mechanically testable. No residual ambiguity found in any of these.
2. **[iter-1 #15] BLOCKING — `checkVersionBumps` top-level return shape is still ambiguous, worse than before.** AC10 now says it "returns `Violation[]` ... (absent ones are listed in **a second return field** `unchecked: string[]`)". "Returns `Violation[]`" says the function returns a bare array; "a second return field" implies the actual return value is an object with (at least) two named fields, one of which presumably holds the violations. A Generator reading "returns `Violation[]`" literally has nowhere principled to attach `unchecked`; a Tester expecting `{violations, unchecked}` destructuring will disagree with one returning a plain array. Needs an explicit object shape, e.g. `{violations: Violation[], unchecked: string[]}`.
3. **[AC3] BLOCKING — media `id`-equals-filename-stem is asserted in the data model but dropped from parseMedia's rejection list.** The component and step schemas both state the invariant in their data-model block and AC1/AC2 both include an id/filename mismatch in their explicit throw list. The media data model states the identical invariant ("`id: … # kebab-case, equals filename stem`") but AC3's rejection list only covers video/photo field mismatches and bad pins — it never mentions a mismatched id. A Generator could reasonably skip that check for media alone and still satisfy AC3 as written.
4. **[errors.ts] MINOR — the `denylisted` code is listed but never required by any AC.** AC5 requires denylisted files to be silently skipped with the sentinel string absent from the model, problems and thrown errors; no AC calls for a `Problem` carrying `code: "denylisted"` to ever be produced, so the code is dangling.
5. **[AC4] MINOR — the default-registry mutation test has no specified reset/isolation mechanism.** Registering `s3` "on the default registry" mutates shared global state with no `unregisterHostingProvider` or reset function offered; harmless if the Tester keeps it to one isolated test file, but the spec doesn't say so.
6. **[render plan] MINOR — "in that key order after canonicalisation" is self-contradictory prose.** The stated options order (`view, explode, annotate, format`) is not alphabetical, yet `canonicalJson` always sorts keys alphabetically. Doesn't affect AC9's hash-based test (which reconstructs the canonical string independently) but will confuse an implementer trying to match the literal render-plan.json field order to "after canonicalisation".
7. **[fixture] MINOR — Step `branch` and the fixture's "scratch/kit branch use" requirement have no consuming AC.** No `stepsForBranch` or equivalent filtering function is specified anywhere in the 15 ACs, so it's unclear whether branch-based filtering is in scope for this task or purely a schema field to store and ignore.

## Iteration 3 — Concerns

1. **[iter-2 #2–#7] RESOLVED.** `checkVersionBumps` now returns the explicit object `{violations: Violation[], unchecked: string[]}` (AC10); media `id`-not-matching-filename-stem is now in AC3's throw list; `denylisted` is gone from the exact `errors.ts` code list and unreferenced elsewhere; `resetHostingRegistry()` is specified (AC4) for test isolation; the Job rules' options-key wording now states `annotate, explode, format, view` — genuinely alphabetical, resolving the self-contradiction with `canonicalJson`; `branch` is explicitly declared stored/pass-through-only with no consuming function in scope. No residual ambiguity in any of these six.
2. **[render plan, MINOR] Worked JSON example still shows the pre-fix, non-alphabetical `options` order.** Job rules now correctly state the key order is `annotate, explode, format, view`, but the illustrative render-plan.json block (line ~113) still prints `options` as `{"view": ..., "explode": ..., "annotate": ..., "format": ...}`. This is a leftover from the prose-only fix to iteration-2 concern #6: the prose is now precise, the example wasn't updated to match, so example and prose now visibly disagree. Non-blocking — AC9's hash test recomputes the hash independently and JSON.parse is order-insensitive, so no mechanical grading depends on this — but worth a one-line fix (update the example) since it's the kind of thing a Generator skims first.
